微软 MAI Code 2：把促销价和可合并代码算进同一本账

MAI Code 2 给日常编码带来新的低价选项，微软引用的价格优势建立在五折促销口径上。 已在 GitHub Copilot 提供的模型适合用真实改动试验，长期账单还要把审阅、修订和合并计入每项工作。[5][6]

四项基准的平均值包含哪些工作

微软在 Ignite 发布七款新模型或产品线。聚焦编码，微软把 MAI Code 2 放在面向 GitHub Copilot 日常企业编码的四个基准里比较。DeepSWE 1.1、Terminal Bench 2.1、SWE-Atlas 和 FrontierCode v1.1 的四项平均，给出下表。微软称，前者对 GPT-6.1 Sol 达到约 98% 质量、约 40% 价格，对 Claude Opus 5.5 达到约 96% 性能、约 5% 价格。[5][6]

Code 2 的四项比较在最高推理设置下进行。前三项在 MSBench 上运行，使用 GitHub Copilot CLI，未用子智能体。FrontierCode 1.1 的分数与成本来自 Artificial Analysis。微软用 MAI Code 2 的五折促销价展示成本，Flash 对比也带有促销价脚注。表里涉及两组题、四个比较对象，分别回答各自的问题。[6]

这套口径适合拿来说明微软认为哪类任务可以降本。它也帮助读者发现试点和基准之间的差距。团队在自己的仓库里也许允许子智能体，可能给工具不同权限，还可能让模型写出修改之外的发布材料。任务环境不同，成本和质量都可能变化。比如自动化测试越完整，模型越容易从失败反馈中收敛，审阅者用来复现问题的时间也可能减少。

短工单可以用较低的成本做更多比较

把任务放回实际仓库，想象一项已有清晰行为约束的改动。实现只有一小处，测试也能立即指出是否合格。模型如果第一次做错，可以很快发现问题。维护者面对的难度是检查它有没有顺手修改无关部分，以及新测试是否真正覆盖请求变化。这样的工作可以先给成本低的候选处理，因为失败后可以及时换人或换模型。

还有一种工单看似相似，实际需要理解历史兼容行为和其他团队的使用方式。哪怕改动只涉及一处，共享接口的边界也要尽早考虑。靠现成测试可能发现不了调用方的差异。对于这类改动，判断模型是否适用的信号是它有没有主动识别不确定之处，能否清楚列出要求团队共同验证的假设。

同样的模型在两项任务里可能花掉类似的费用，留给维护者的工作却会截然不同。对企业而言，价格的下降可以扩大用模型处理常规改动的范围。处于关键链路、需要协调多方的项目，预算还要给审阅与联调留足时间。微软也明确表示，MAI Code 2 仍未针对基础科学研究和很长周期的智能体工作调优。[6]

对在一个季度内持续发布的团队，可把账单分成几段看。

  • 第一次尝试。 记录模型用在哪类改动，测试前后生成了哪些变更。
  • 从失败到交回。 观察它在测试不过、资料不足或分支条件复杂时，是否留下可以继续的内容。
  • 从交回到合并。 统计维护者用于核实、修订、补测试和沟通的时间。
  • 合并之后。 留意哪些问题只能到接入其他系统才被发现，避免把后续修复漏出总账。

前端盲测回答的是偏好，试点还要看维护

微软公布的前端盲测有 258 名标注者。针对界面、游戏、可视化、三维和 SVG 等题目，评审对 MAI Code 2 结果的偏好比例为 64%，比较对象是 GPT-6 Sol。这个对象和上表的 GPT-6.1 Sol 不同。把两者放到一张预算表之前，要保留模型名与任务范围的区别。[6]

盲测可以把视觉感受纳入评估。一个团队平时若经常需要演示页面或内部概念稿，初稿更易看懂就有价值。做产品界面时，团队还关心修改是否延续既有设计系统，能否使用键盘操作，展示少量与大量数据时布局是否稳定。这些是团队自身的验收任务，盲测偏好提供不了每一项的答案。

比如让模型修一个高流量页面，输出效果可能很漂亮，却引入多套做同一件事的组件。视觉评审看到的是完成稿，维护者后来要决定是否保留新组件、样式应归在哪里，以及其他页面需要不需要跟着修改。试点如果既记录视觉结果，也记录兼容原有代码所需的修订，能够帮助产品和开发达成同一套交付标准。

Flash、Copilot 和办公室场景各有一个着力点

MAI Code 2 已在 GitHub Copilot 提供，Code 2 Flash 在 Microsoft Foundry 限量预览。微软称 Flash 在三个高流量编码基准的表现可比 GPT-6 Luna 和 Claude Haiku 5.5，价格分别约为对方的 65% 和 20%。微软还提到将陆续提供其他接入入口。采用评估时，已经能用的渠道、预览渠道和未来计划分别对应不同风险，尤其在需要大量同事同时体验时。[6]

微软又以 Code 2 Flash 为基础调优出 MAI Work Flash，用于 M365 与 Fabric IQ。微软称，它在五个 Word 内部基准上表现与 GPT-6.1 Sol 类似，每次调用少用约 42% 输入词元。在 Teams 的指令遵循和工具调用上，微软称最多可少用 28% 词元。这里强调的是围绕工作软件中的特定任务优化。编码评估提供的是另一个任务集合。[5]

在工程团队看来，这种分化有一个实际好处。产品可以把某些重复、可观察的工作给成本更低的模型，少数复杂问题升级。对管理预算的人，这意味着不能只按用户数估算。两个小组人数类似，如果一个组大多生成简单补丁，另一个经常做多阶段迁移，模型交易费用和维护者投入的比例都会不同。

办公场景也需要一样的拆分。比如会议回顾和正式交付文件可能都在同一套软件里，后者往往需要更多核查。若一款小模型把结构化提取做得更省，团队可以先在这个边界上评估。若交付物要经历多次评审、引用许多尚在变化的资料，就应把复核时间和版本记录放在一起看。

试点时还可以按工单样本记录相同的审阅标准，避免某个维护者只看测试结果，另一个维护者却会复查所有边界。若两种审阅方式拿到的通过率差很多，团队可以先找出最常漏看的问题，再决定哪些检查可以自动化。这个发现即使与模型名次无关，也会直接影响上线成本。对组件库或公共接口，维护者的检查往往值得独立计时。代码生成结束只是开始，合并责任和后续沟通都由使用这个仓库的人承担。

促销期买到的机会，常态需要另一张账单

五折促销价适合作为试验期的费用依据。团队可以在较低成本下多比较几类真实工单，知道哪些可顺利交付。长期预算还需要按常态条件估算，并考虑同一工作是不是会在不同渠道使用不同的推理设置。渠道费率、实际词元数、重试和人工投入，最终都会落到聚合统计里。

设想一个维护者在一周里接受了多个改动。有的草稿可以当天合并，有的要换工具重新开始，有的只适合留下设计讨论。这几类成果仍然有价值，但价值各不一样。用实际合并结果和审阅时间来描述它们，可以帮助团队分辨低价带来的是有效吞吐量，还是更多需要人清理的尝试。

要让这个对比有用，经常处理重复工单的团队可以特意留下一类“应当停手”的任务。比如原始需求明确缺少可重现的输入，模型适合整理已知条件并提出下一步需要的信息。这项工作即使没有产生可合并代码，也可以降低接手成本。用单一通过率打分会掩盖这种价值，团队有必要说明什么算一次有效交付。

MAI Code 2 的发布把更便宜的日常编码列成了一个可测试的选项。促销价让试验更容易展开，独立记录审阅和修订才能回答折扣过去之后的账单问题。等维护者在同一套标准下能更快合并可用改动，微软的性能与价格数字才会对团队预算产生具体意义。

试验里还应具体记录改动在合并前由谁签字。低价模型扩大了可试范围，审阅责任仍落在仓库所有者身上。交接清楚能减少额外沟通，也使不同小组的报价更好理解。
